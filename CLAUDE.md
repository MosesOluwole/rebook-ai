# Rebook AI — project rules for Claude Code

Rebook AI is a multi-tenant booking SaaS: one Next.js modular monolith on one Supabase Postgres,
plus a separate worker (from Phase 6). Launch verticals: private midwives (timed, invite-only,
health-adjacent data) and event planners (enquiry, quote, accept, deposit marked manually).

## Sources of truth, in order

1. `docs/architecture.md` — System Design v1.0. Design decisions and invariants.
2. `docs/phases.md` — the ten build phases, their scope and acceptance criteria.
3. `docs/adr/` — decisions made while building (ADR-001 is the stack).
4. `docs/setup.md` — how to run the project locally and in CI.
5. `AGENTS.md` — generated by `next dev`; points at the Next.js 16 docs in
   `node_modules/next/dist/docs/`. Read the relevant guide before using a Next API you are not
   certain about: this Next.js version differs from older training data.

Where code and these documents disagree, the documents win and the code is a finding.

## Non-negotiables

- **Moses commits.** Never run `git commit`, `git push`, `git reset`, `git checkout`, `git clean`
  or anything that discards work. Agents leave changes in the working tree.
- **One phase at a time.** Do only the current phase from `docs/phases.md`. Do not pre-build later
  phases (for example, no roles, RLS or tenant tables before Phase 1 begins).
- **Gate before hand-over.** Run the `rebook-test-engineer` subagent against the phase's acceptance
  criteria, then the `rebook-code-reviewer` subagent, fix blocking findings, and hand Moses both
  reports.
- **Dependencies are pinned to exact versions** and explained in the PR. Prefer established
  releases; pnpm refuses anything published less than a day ago (`minimumReleaseAge`).
- **No personal data anywhere outside the database**: not in logs, errors, fixtures, test output,
  URLs or analytics. Fixtures are synthetic. No clinical fields for health business types.

## Toolchain and commands

Node 24 (`.nvmrc`) and pnpm 11 (`packageManager`, via `corepack enable`). All commands are pnpm
scripts; see `docs/setup.md` for first-time setup.

| Command                  | What it does                                                          |
| ------------------------ | --------------------------------------------------------------------- |
| `pnpm dev`               | Next.js dev server on http://localhost:3000 (`/health` is the probe)  |
| `pnpm typecheck`         | `next typegen` then `tsc --noEmit`                                    |
| `pnpm lint`              | ESLint (typescript-eslint strict, type-aware), zero warnings allowed  |
| `pnpm lint:deps`         | dependency-cruiser module-boundary rules                              |
| `pnpm format` / `:check` | Prettier                                                              |
| `pnpm test`              | Vitest unit project (pure, no database)                               |

| `pnpm test:e2e`          | Playwright, desktop and 375 px projects                               |
| `pnpm check`             | typecheck, lint, lint:deps, format:check, unit tests                  |

## Code layout and boundaries

```
src/app/                      Next.js routes, layouts, route handlers, server actions: thin adapters.
                              Parse input with Zod, call a module's public function, shape the response.
src/modules/<module>/
  index.ts                    The module's ONLY public surface and its composition root.
  domain/                     Pure rules and types. No framework, I/O, clock or package imports (zod excepted).
  application/                Use cases. Depend on domain and on ports (interfaces), receive deps as arguments.
  infrastructure/             Adapters: database schema and repositories, clocks, providers.
src/shared/config/env.ts      The only place that reads app configuration from process.env (Zod, at boot).
                              getEnv() is server-only. APP_DATABASE_URL is the app's connection;
                              DATABASE_URL is the owner connection for tooling and fixtures only.
src/shared/db/client.ts       The only place a Postgres connection is created.
src/modules/tenancy/          withTenant, TenantTx, the tenant context and the core tenant-owned tables.
src/shared/kernel/            Pure ports and types any module may use (e.g. Clock).
tests/unit, tests/integration, tests/e2e, tests/helpers, tests/fixtures
supabase/migrations/          SQL migrations, applied by the Supabase CLI.
```

`pnpm lint:deps` enforces, with error severity: cross-module imports only via `index.ts`; no
module internals imported from `src/app` or `src/shared`; `domain/` depends only on its own
module's domain and `src/shared/kernel`; `src/shared` never imports modules; no cycles; no isolated
files under `src` (a file with no imports in or out); no devDependencies in shipped code. Rules live in `.dependency-cruiser.cjs` and are
proven by `tests/unit/dependency-rules.test.ts`. `src/modules/platform` is the reference module.

Modules planned by the design (§3): booking, crm, messaging, ai, analytics, plus tenancy (Phase 1)
and platform (health and operations). Create a module only when its phase needs it.

## Coding standards

- TypeScript strict plus `noUncheckedIndexedAccess`, `verbatimModuleSyntax` (use `import type`) and
  `erasableSyntaxOnly` (no enums, namespaces or parameter properties: use union types and plain
  objects). No `any` without a comment saying why.
- Environment: import `getEnv()` from `src/shared/config/env.ts`. To add a variable, extend the
  schema and `HINTS`, then `.env.example` and `docs/setup.md`. Secrets never go in `NEXT_PUBLIC_*`.
- Time: domain functions take instants as arguments; application code takes a `Clock`. Never call
  `Date.now()` or `new Date()` in domain code. Store `timestamptz`, compute in the location's zone.
- Money: `numeric(12,2)` plus currency; never floats.
- Validation: Zod at every boundary (route handlers, server actions, jobs, webhooks, env).
- Errors: typed, never swallowed. Logging: only `console.warn`/`console.error` until structured
  logging arrives with the worker; never log request bodies or personal data.
- Database: every connection comes from `createDbClient`. Every query against tenant data runs
  inside `withTenant` (web) or `withWorkerTenant` (jobs) from `src/modules/tenancy`, and every
  repository function takes the branded `TenantTx` it provides. Never query `rebook` tables with
  a bare database handle, never connect as the owner at runtime, and never read `tenant_id` from
  a request body, header, query string or job payload without re-verifying it.
- Tables: all in the `rebook` schema (never `public`). Every tenant-owned table has
  `tenant_id uuid not null`, `unique (tenant_id, id)`, RLS enabled and forced, policies comparing
  against `(select nullif(current_setting('app.tenant_id', true), '')::uuid)`, grants only to
  `rebook_app`/`rebook_worker`, and children reference parents as
  `(tenant_id, parent_id) → parent (tenant_id, id)`. UUIDv7 ids via `rebook.uuid_generate_v7()`.
  Add the table to `tests/integration/tenancy/isolation.generated.test.ts` fixtures and
  `tests/helpers/tenant-fixtures.ts`, run `pnpm db:check-schema` and `pnpm db:docs`.
- Migrations are generated into `supabase/migrations` by `pnpm db:generate` for table DDL
  (hand-written SQL for roles, policies, grants, functions: `pnpm db:generate --custom
--name=<what>`), applied only by the Supabase CLI, forward-only, expand then contract. No
  passwords or secrets in migrations.
- Next.js: `cacheComponents` is off (tenant data must never be cached across requests); route
  handlers that must reflect live state export `dynamic = 'force-dynamic'`.
- Formatting is Prettier's; do not fight it. Run `pnpm check` before asking for review.

## Tests

- Unit tests sit next to the code (`*.test.ts`) or in `tests/unit`; they touch no database.
- Integration tests in `tests/integration` run against the real local Postgres through
  `tests/helpers/db.ts`: `connectAppDb()` (as `rebook_authenticator`, through `withTenant`) for
  every behaviour under test, `connectOwnerDb()` only for catalogue checks and the owner-only
  fixtures in `tests/helpers/tenant-fixtures.ts`. Never mock the database for RLS, isolation,
  constraints, idempotency, triggers or concurrency. Never assert behaviour as the owner.
- E2E tests in `tests/e2e` run in both Playwright projects (desktop and 375 px). No retries: a
  flaky test is a failing test.
- Never skip, `.only`, loosen or delete an assertion to get green. Fixtures are synthetic.

## Working with the agents

- `rebook-test-engineer`: "use the rebook-test-engineer subagent to verify Phase N against its
  acceptance criteria". It may create or edit files only under test directories, and reports
  PASS or FAIL with evidence.
- `rebook-code-reviewer`: "use the rebook-code-reviewer subagent to review the Phase N changes".
  Read-only; reports APPROVE or CHANGES REQUIRED with findings at file:line.
- Both read `docs/` and this file first. Keep those documents current in the same change.
