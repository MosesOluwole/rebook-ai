# ADR-001: Stack and tooling for the MVP

- **Status:** Accepted (Phase 0 committed as 608e891).
- **Date:** 2026-10-29
- **Deciders:** Moses Oluwole (owner); drafted by Claude Code during Phase 0.
- **Source design:** `docs/architecture.md` (System Design v1.0), especially §3 Architecture,
  §4 Tenancy, §11 Reliability and §12 Alternatives and spec decisions.

## Context

Rebook AI must ship an MVP by 11 December 2026 with correctness guarantees that cannot be
retrofitted: tenant isolation, no double bookings, immutable attribution and no duplicate emails.
The system design already fixes the shape of the system (one Next.js modular monolith, one
Supabase Postgres with RLS, a separate worker, correctness in the database). Phase 0 turns those
choices into concrete, pinned tooling and records the decisions that the design leaves open.

## Decision

| Concern                 | Decision                                                                                    | Pinned version                  | Design reference |

| Database, auth, storage | Supabase Postgres (RLS, composite tenant FKs), Supabase Auth for staff                      | Postgres 17 (local image 17.11) | §3, §4, §5       |
| Data access             | Drizzle ORM over postgres.js, SQL migrations                                                | 0.45.4 / 3.4.9                  | §4, §12 item 1   |
| Validation              | Zod at every boundary, including env                                                        | 4.6.7                           | §3               |

| Email                   | Resend behind a `MessageChannel` interface, dev adapter locally                             | Phase 6                         | §8, §11          |
| Hosting                 | Vercel (web), Supabase eu-west-2, Fly.io or Railway (worker)                                | Phase 9                         | §11              |
| Tenant isolation        | Shared schema, RLS with `withTenant` transaction context, runtime roles without `BYPASSRLS` | Phase 1                         | §4, §12          |

### Dependencies added in Phase 0 and why

Runtime: `next`, `react`, `react-dom` (framework); `zod` (validation); `drizzle-orm`, `postgres`
(data access; used by the test database helper now, by repositories from Phase 1).

Development: `typescript`, `@types/node`, `@types/react`, `@types/react-dom`; `eslint`,
`eslint-config-next`, `typescript-eslint`, `eslint-config-prettier`, `prettier`;
`dependency-cruiser`; `vitest` and its peer `vite`; `@playwright/test`; `drizzle-kit`;
`supabase` (CLI); `@next/env` (loads `.env` outside Next for tests and Drizzle Kit).

## Consequences

- Positive: reproducible environment from a fresh clone; boundaries, types, formatting and
  dependency hygiene are enforced by CI from day one; one migration story for local, CI, preview
  and production; environment mistakes fail at boot with a named variable.
- Negative or accepted costs: ESLint 10 produces three peer-range warnings until Next updates its
  bundled plugins; `supabase start` needs Docker and about 1 GB of images; integration and E2E
  tests require the local stack to be running; TypeScript 7 adoption waits on `typescript-eslint`.
- Revisit when: `typescript-eslint` supports TypeScript 7; pnpm 12 has been stable for a quarter;
  Vitest 5 and postgres.js 4 have been out for a quarter; Phase 5 decides caching for public
  booking pages; Phase 9 fixes the worker host.
